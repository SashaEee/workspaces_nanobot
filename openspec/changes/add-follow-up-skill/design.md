## Context

Follow Up — приложение с MCP-сервером по stdio (`backend/skill/mcp_server.py`,
семь инструментов): SQLite + FAISS + BM25, Greenplum, эмбеддер
`bge-m3-russian-legal` и реранкер `bge-reranker-v2-m3`. Проверено на живом
стенде: gateway поднимает его через `tools.mcpServers`, агент зовёт
`mcp_follow_up_ask`, ответ с источниками доходит в чат Единого рабочего
места за ~20 с.

Требование к поставке — как у соседних навыков: «Получить из master» и
перезапуск gateway, без клонов, без машинных файлов и без правок конфига.

## Goals / Non-Goals

**Goals**

- Код навыка — в папке навыка; один статичный блок в `config.json`.
- Ноль изменений в runtime-коде проекта и в корневом `requirements.txt`.
- Настройки подключения — из настроек агента; в коде нет ничего от
  конкретной площадки.
- Машина, где навык не может подняться, стартует как раньше.

**Non-Goals**

- Встраивание навыка классом `Tool` в процесс gateway.
- Второй механизм регистрации инструментов помимо `tools.mcpServers`.

## Decisions

**D1. Код — в `workspace/skills/follow_up/backend/`.** Так же, как код
соседних навыков лежит в их папках. Импорты внутри — абсолютные
(`backend.*`), `PYTHONPATH` ставит лаунчер; из `lib/`, `workspace/tools/` и
других навыков навык ничего не импортирует, и наоборот.

**D2. Транспорт — MCP stdio, отдельный процесс, интерпретатор агента.**
Библиотеки общие, процесс — свой: у навыка локальная SQLite с единственным
писателем и фоновые потоки синхронизации корпуса с Greenplum. Падение или
зависание навыка не должно ронять gateway, а два писателя в одной базе
внутри одного процесса — ломать её. Лаунчер выбирает интерпретатор так:
`FOLLOW_UP_PYTHON` → `.venv` рядом → Python процесса gateway (по его
`argv[0]`: `/proc/<pid>/exe` у venv — симлинк на системный Python и теряет
site-packages) → собственный. Кандидат без библиотек навыка пропускается
(проверка через `importlib.util.find_spec`, без импорта).

**D3. Команда в `config.json` — лаунчер внутри папки навыка, относительно
корня репозитория.** Рассмотрены и отклонены:
- `${FOLLOW_UP_PYTHON}` — `resolve_config_env_vars` бросает `ValueError` на
  неизвестной переменной: машины без неё не стартовали бы;
- `"command": "python"` / `"python3"` — имя интерпретатора различается
  между Linux/macOS и Windows;
- абсолютные пути — привязка к машине в git.
Лаунчер — файл с shebang для POSIX плюс `follow_up_mcp.cmd` для Windows;
`shutil.which` в `_normalize_windows_stdio_command` подбирает `.cmd` по
`PATHEXT`. Допущение то же, что у `exec`-инструмента: gateway запускается из
корня репозитория.

**D4. Настройки — у агента.** Лаунчер передаёт `NANOBOT_HOME` (вычислен от
собственного пути). Сервер берёт оттуда:
- модель — как раньше, из `config.json` / `.secrets.env`;
- Greenplum — из DSN канала шины `channels.postgres.dsn` (`${DATABASE_URL}`
  раскрывается из `.secrets.env`), схему — из `channels.postgres.schema`.
  Включается, только если сервер отвечает как Greenplum (`SELECT version()`):
  DDL навыка гринпламовский, а на машине разработчика шина — обычный
  PostgreSQL, и тогда навык работает в локальном режиме;
- модели — из `workspace/data_store/cache/caches_pipelines/` (реранкер —
  тот же, что у соседних навыков, второй копии не нужно).
Явная настройка навыка (переменная окружения или его `.env`) важнее агента.
Пароль из DSN в журнал не пишется.

**D5. В коде нет ничего от площадки.** Витрины-источники навык читает
через представления `v_fu_assignment` и `v_fu_act_violation` в своей же
схеме; их один раз создаёт администратор площадки. Код знает только эти
имена — ни адресов, ни баз, ни схем.

**D6. Линтер и тесты.** `backend/` сопровождается в репозитории Follow Up со
своим набором тестов и линтером; вложенный `ruff.toml` (с `extend` на
корневой `pyproject.toml`) исключает его из `ruff check` проекта. Тест
проекта `tests/test_follow_up_skill.py` закрепляет контракт интеграции, а
не поведение навыка.

**D7. Навык не поднялся — не ошибка проекта.** Нет кода — лаунчер печатает
причину в stderr (stdout — канал JSON-RPC, туда ни байта) и выходит с
кодом 3; `open_single_server` ловит исключение, пишет `failed to connect`
и gateway продолжает старт. Нет библиотек или подключения —
`follow_up_mcp --check` называет, чего не хватает.

**D8. Реестр один.** Навык объявлен в `project.json::skills` (без таблиц и
индексов); инструменты приходят через штатный `tools.mcpServers`.

## Risks / Trade-offs

- Библиотеки навыка (`torch`, `sentence-transformers`, `rank-bm25`,
  `pydantic-settings`, `sqlalchemy`) должны стоять в окружении агента. На
  площадке `torch` и `sentence-transformers` уже есть для соседних
  навыков; остальное — `pip install -r workspace/skills/follow_up/requirements.txt`.
- Объём: ~21 тыс. строк кода навыка в репозитории проекта. Он изолирован
  в папке навыка и не импортируется остальным кодом.
- Относительный путь в `command` требует запуска gateway из корня
  репозитория — как и сегодня для `exec`.
- На Windows между gateway и сервером стоит `cmd.exe` → `python`; при
  жёстком завершении gateway дочерний процесс может пережить обёртку.
  Штатное завершение (`close_mcp`) закрывает stdio, и сервер выходит сам.
- Дословность вывода — инструкция модели, не механизм (как у остальных
  навыков).
