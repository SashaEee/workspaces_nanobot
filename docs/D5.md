# D5 — полное описание `follow_up`

## 1. Назначение документа

Этот документ описывает навык `follow_up` (далее — D5): что лежит в этом
репозитории, как gateway его запускает и откуда навык берёт настройки.

D5 лежит здесь **целиком**: инструкция агенту и код сервера в
`workspace/skills/follow_up/`, инструменты агента в
`workspace/tools/follow_up.py`. Существующие файлы проекта не меняются.
Клонировать на машину с gateway ничего не нужно: модель, подключение к базе
и схема берутся из настроек агента. Один раз на площадке готовятся схема,
представления над витринами и модели (раздел 14) — это делает скрипт из
репозитория Follow Up, в эту ветку он не входит.

Описание не содержит реальных актов, номеров проверок, строк подключения,
API-ключей, внутренних адресов и имён схем. Пути даны заглушками вида
`<путь>`.

## 2. Назначение D5

D5 отвечает по **текстам актов проверок и поручений**:

- что нашли в конкретной проверке, какие отклонения, что написано в акте;
- цитата из акта: где именно это сказано, в каких актах встречается тема
  или человек;
- гипотезы и перечень того, что стоит проверить, на старте новой проверки;
- карточка контроля исполнения по ответу профильного подразделения
  (письмо `.docx`, `.txt`, `.pdf`);
- реестр отклонений с фильтрами: категория, критичность, сумма, система,
  подразделение.

Граница с `audit_analyzer` простая: **текст акта и цитата — D5, агрегаты
по витринам и произвольный SQL — `audit_analyzer`**. Отказ одного навыка не
повод подменять его другим: «не нашёл» у D5 значит, что в корпусе актов
этого нет.

## 3. Положение в архитектуре

```text
чат Единого рабочего места (кнопка К1-2)
    │  вопрос в шину
    ▼
gateway (--profile=prod) → агент
    │  выбирает инструмент по SKILL.md и описаниям
    ▼
mcp_follow_up_ask / _hypotheses / _deviations / …   ← workspace/tools/follow_up.py
    │  MCP по stdio, одна сессия на процесс gateway
    ▼
workspace/skills/follow_up/scripts/follow_up_mcp     ← лаунчер
    │  тот же Python, что у gateway
    ▼
python -m backend.skill.mcp_server                   ← отдельный процесс
    (cwd = workspace/skills/follow_up, NANOBOT_HOME = корень репозитория)
```

**Инструменты агента** — обычные `Tool` проекта, их находит загрузчик
`workspace/tools/*.py`, как инструменты D3 и D6. При старте gateway модуль
поднимает сервер D5 и держит с ним MCP-сессию в своём потоке (в CLI и
тестах проекта — по первому вызову); каждый из семи инструментов передаёт
аргументы одноимённому инструменту сервера и возвращает его ответ.

**Почему сервер — отдельный процесс, а не код внутри gateway.** Библиотеки
у D5 и gateway общие, процесс — свой. У D5 локальная база SQLite с
единственным писателем и фоновые потоки, которые синхронизируют корпус с
корпоративной БД. Внутри gateway падение или зависание навыка уронило бы
агента, а второй писатель в той же базе испортил бы её.

**Почему не `tools.mcpServers` в `config.json`.** В `nanobot-ai` 0.3.5
серверы оттуда поднимает `MCPProvider` собственных CLI фреймворка, а
gateway проекта собирает `AgentLoop` сам и MCP не подключает — запись
просто не сработала бы. Поэтому сессию держит модуль инструментов, и
`config.json` не меняется.

| `workspace/skills/follow_up/backend/` | код сервера D5 |

| `workspace/skills/follow_up/ruff.toml` | `backend/` вне линтера проекта, лаунчер — под ним |

библиотеки D5 перечислены в его собственном `requirements.txt`.

## 5. Подключение

### 5.1. Инструменты агента

`workspace/tools/follow_up.py` импортирует только стандартную библиотеку,
`nanobot`, `mcp`, `anyio` и `loguru` (зависимости `nanobot-ai` и `mcp`);
код сервера в процесс gateway не попадает. Журнал — через `loguru`, как у загрузчика
проекта.

- Семь классов `mcp_follow_up_<имя>` строятся из `tools.json` навыка —
  описания и схемы ровно те, что отдаёт сервер (файл генерируется из кода
  сервера при сборке навыка).
- В gateway (`gateway.py`) сервер поднимается в фоне сразу при
  регистрации — один раз на процесс: иначе синхронизация корпуса
  стартовала бы только после первого вопроса, а первый вопрос ждал бы
  подъёма. В CLI и тестах проекта (`ApplicationContext`) — по первому
  вызову: лишний экземпляр на машине с корпусом стал бы владельцем базы и
  начал синхронизацию. `FOLLOW_UP_WARM_UP=1`/`0` решает явно.
- Сервер запускается командой `<Python gateway> workspace/skills/follow_up/scripts/follow_up_mcp`
  с абсолютными путями и **полным окружением gateway**; его stderr
  дописывается в `workspace/skills/follow_up/logs/server.log` (у каждого
  старта строка-заголовок; больше 2 МБ — в `server.log.1`). Не открылся
  журнал — stderr идёт в журнал gateway.
- Ключ беседы (`session_key`) и отправитель (`user_id`) берутся из
  контекста хода nanobot, а не от модели (её значения заменяются): модель
  свой ключ не видит, а придуманный ею совпал бы у двух аудиторов.
- Умерший сервер поднимается заново тем же вызовом: запрос, который не
  успел уйти в мёртвую сессию, повторяется на свежем сервере. Вызовы, шедшие
  в момент смерти, сразу получают отказ, а не ждут своего таймаута. Каждый
  запуск сервера гасит только сам себя — поздняя очистка старого запуска не
  трогает новый. Завис на подъёме дольше 180 с — запуск отменяется, процесс
  гасится.
- Ответ сервера возвращается текстом как есть; ошибка — `ToolResult.error`
  с причиной (для неподнявшегося сервера — с хвостом его журнала) и
  подсказкой `follow_up_mcp --check`.

Настройка — секция `tools.follow_up` (читается через `Settings`, как у
соседних инструментов): `enable` (по умолчанию `true`) и `timeout_sec`
(по умолчанию 240). Без файлов навыка инструменты не регистрируются.

### 5.2. Лаунчер

`scripts/follow_up_mcp` — только стандартная библиотека, запускается
любым Python ≥ 3.8. Что он делает:

1. находит код D5 рядом — `workspace/skills/follow_up/backend/`;
2. выбирает интерпретатор: `FOLLOW_UP_PYTHON`, если задан; иначе `.venv`
   рядом с кодом; иначе Python процесса, который его запустил (по его
   `argv[0]`: у venv `/proc/<pid>/exe` — симлинк на системный Python без
   site-packages окружения), либо собственный. Между двумя последними
   предпочитается тот, у кого есть библиотеки D5 (проверка через
   `importlib.util.find_spec`, без импорта); если библиотек нет ни у
   кого — берётся первый, и `--check` скажет, чего не хватает. Явный
   `FOLLOW_UP_PYTHON` и `.venv` не проверяются. Под gateway лаунчер
   запускается его же Python, поэтому интерпретатор совпадает;
3. вычисляет `NANOBOT_HOME` от собственного расположения — три уровня
   вверх от папки навыка, независимо от текущего каталога;
4. выставляет `NANOBOT_HOME`, `MODELS_DEVICE` (по умолчанию `cpu`),
   `PYTHONUTF8` и дописывает корень кода в начало `PYTHONPATH`;
5. переходит в папку навыка и запускает `python -m backend.skill.mcp_server`
   (на POSIX — через `exec`, тем же процессом). Все пути к этому моменту
   абсолютные.

`follow_up_mcp.cmd` — обёртка для ручного запуска на Windows через `python`
из `PATH`.

### 5.3. Отдельный клон (необязательно)

Если D5 нужно запускать из отдельного клона Follow Up со своим окружением,
пути задаются в `workspace/skills/follow_up/follow_up.env.local` (под
`*.env.*` в `.gitignore`) или переменными окружения gateway — окружение
важнее файла, файл важнее встроенного кода:

```text
FOLLOW_UP_ROOT=<путь к клону Follow Up>
FOLLOW_UP_PYTHON=<интерпретатор его окружения>
MODELS_DEVICE=cpu
```

### 5.4. Проверка

Проверить, что увидит gateway, ничего не запуская:

```bash
python workspace/skills/follow_up/scripts/follow_up_mcp --where
python workspace/skills/follow_up/scripts/follow_up_mcp --check
```

Запускать тем же Python и из того же окружения, что и gateway, — тогда
ответ совпадёт с тем, что увидит он. `--where` — где код и каким Python он
запустится. `--check` — то же плюс самопроверка сервера: библиотеки, модель
агента, подключение к базе и чтение витрин, модели, запись в каталог
данных. Ответ — JSON с итогом `ok` и списком проблем.

Если кода нет или интерпретатор не найден, лаунчер выходит с кодом 3 и
пишет причину в stderr; stdout остаётся чистым, потому что это канал
JSON-RPC. Вызов инструмента тогда вернёт «Follow Up сейчас недоступен» с
причиной.

## 6. Инструменты

| Инструмент | Что делает | Когда |
|---|---|---|
| `mcp_follow_up_ask` | вопрос по корпусу актов и поручений, ответ со ссылками на источники | основной путь |
| `mcp_follow_up_hypotheses` | гипотезы и что проверить по теме новой проверки | «начинаю проверку по теме X» |
| `mcp_follow_up_deviations` | реестр отклонений с фильтрами, без обращения к модели | нужна таблица, а не рассуждение |
| `mcp_follow_up_status` | что есть в корпусе и в каком режиме хранилище | отличить «не нашлось» от «этого тут нет» |
| `mcp_follow_up_card_start` | запустить сборку карточки исполнения, сразу возвращает `job_id` | прислан ответ подразделения |
| `mcp_follow_up_card_status` | стадия и результат по `job_id`, сам ждёт до 20 с | после `card_start`, пока `done=false` |
| `mcp_follow_up_forget` | забыть контекст диалога | аудитор перешёл к другой проверке |

Префикс `mcp_` сохранён: так эти инструменты назывались, когда сервер
подключался штатным MCP фреймворка, и так они названы в `SKILL.md`.

## 7. Настройки — у агента

Файлы агента читаются из `NANOBOT_HOME` в том же порядке, что у gateway:
`project.json` → `session_manager.json` → `config.json` → `.secrets.env`,
затем `${VAR}`.

**Модель.** Своей модели у D5 нет — тем же правилом, что у
`audit_analyzer`: `agents.defaults.provider` и `model` плюс
`providers.<provider>.apiBase` и `apiKey`. Модель агента **всегда важнее**
настроек D5; переопределить можно только
`skills.follow_up.llm.{max_tokens, temperature}` (единственная форма,
которую пропускает `SkillSettings`), а целиком отказаться от модели агента
— `LLM_IGNORE_NANOBOT=true`. Ключ в журнал не пишется.

**База и схема.** Подключение — из DSN канала шины
`channels.postgres.dsn` (`${DATABASE_URL}` раскрывается из `.secrets.env`),
схема — из `channels.postgres.schema`. Явная настройка D5 (переменная
окружения или `.env` в папке навыка) здесь важнее агентской. Оговорки:

- схема `public` своей не считается: в шаблоне шина живёт там, а таблицам
  D5 в `public` не место. Тогда схему задаёт `.env` в папке навыка
  (`GP_WRITE_SCHEMA`);
- корпоративная БД включается, если сервер **не** отвечает как обычный
  PostgreSQL (`SELECT version()`): DDL D5 гринпламовский, а на машине
  разработчика шина — обычный PostgreSQL, и тогда D5 работает по
  локальному корпусу. Если база не ответила вовсе, она считается Greenplum
  — выключать корпус на весь сеанс из-за минутной недоступности нельзя.
  Явный `GP_ENABLED` отменяет проверку.

Пароль из DSN в журнал не пишется.

**Модели.** Эмбеддер `bge-m3-russian-legal` и реранкер
`bge-reranker-v2-m3` ищутся по порядку: явная настройка → `models/<имя>` в
папке навыка (в git не попадает) →
`workspace/data_store/cache/caches_pipelines/<имя>`.
Реранкер тот же, что у соседних навыков, — вторая копия не нужна. Эмбеддер
свой: векторы корпуса посчитаны им, подменять его другим bge-m3 нельзя.

Модели D5 работают **на CPU** (`MODELS_DEVICE=cpu`): видеокарты на машине
gateway заняты обслуживанием основной модели.

## 8. Сессии и память диалога

D5 помнит, о какой проверке шла речь, и доигрывает уточнения. Память
ключуется `session_key`, и его подставляют инструменты агента — из
контекста текущего хода nanobot. У каждой беседы память своя;
`mcp_follow_up_forget` забывает только текущую. Модель ключ не передаёт и
не выдумывает.

## 9. Время ответа и долгие операции

`ask` и `hypotheses` синхронны: сервер укладывает ход в свой дедлайн
(150 с), инструменты агента ждут до `timeout_sec` (240 с). Обычный вопрос
занимает 10–60 секунд. Вопросы про исполнение поручений (`ask` со словами
вроде «поручение», «ответ профильника», «проверь исполнение») идут веткой
контроля исполнения: её сервер по дедлайну не обрывает, но новые вызовы
модели в ней после дедлайна хода (150 с) не начинаются — долгий ответ придёт
сокращённым, а не поздним. Полную карточку исполнения собирать через
`card_start`.

Карточка исполнения строится минутами и поэтому идёт задачей с опросом:

1. `mcp_follow_up_card_start` возвращает `job_id` сразу.
2. `mcp_follow_up_card_status` **сам ждёт** готовности до 20 секунд
   (`wait_sec`, максимум 60). Готово — карточка в `answer_md`; не собралась
   — `done: true`, `ok: false` и причина в `reason`.

Ожидание на стороне сервера, потому что у агента нет паузы между вызовами:
получив «не готово», он позвал бы снова немедленно и за секунды сжёг
лимит итераций.

## 10. Контракт доставки

Успешный ответ приходит полем `answer_md` — готовым текстом. `SKILL.md`
требует выводить его дословно, без summary-pass и своего вступления, — тот
же контракт, что у D3 и D6.

Это **инструкция модели, а не механизм**: переформулировка возможна.
Факты и нумерация источников на практике сохраняются.

Прочие поля:

| Поле | Значение |
|---|---|
| `answer_md` | ответ целиком — в том числе уточняющий вопрос («по какой КМ?») и «в корпусе этого нет» |
| `insufficient: true` | найдено мало (или модель была недоступна и D5 отвечает тем, что собрал) — D5 говорит об этом сам |
| `ok: false` + `reason` | технический отказ: не уложился в дедлайн, не хватает аргументов, карточка не собралась |

## 11. Данные

У D5 свой локальный корпус (SQLite, FAISS, BM25) в
`workspace/skills/follow_up/data/` — в git не попадает. Общий корпус —
таблицы `t_fu_*` в схеме D5 корпоративной БД; при старте они создаются,
если их нет, фоновые потоки подтягивают оттуда корпус и пополняют его.
Витрины-источники — только на чтение: D5 читает их через представления
`v_fu_assignment` и `v_fu_act_violation` в своей же схеме, поэтому в коде
нет ни одного имени витрины, базы или адреса. Вердикты аудиторов пишутся
только в собственную таблицу D5.

Локальная SQLite открыта без файловых блокировок (так она работает на
сетевом хранилище), поэтому **владелец у файла базы один**. Живой владелец
— процесс на этом хосте с живым PID либо процесс на другом хосте, чья
отметка в файле владельца (обновляется раз в 30 с) свежее двух минут.
Файл владельца пишется атомарно; если он не читается, база тоже считается
занятой. Если файлом владеет другой живой процесс Follow Up, сервер
отказывается стартовать с кодом 2 — два писателя без блокировок портят
базу. Если владение перехватили на ходу (пауза дольше двух минут), процесс
это замечает и останавливает свои фоновые писатели. Поэтому с одним
каталогом навыка работает один gateway, даже если каталог общий на
нескольких узлах.

```text
│   ├── skill/mcp_server.py          — MCP-сервер, семь инструментов
│   ├── skill/selfcheck.py           — самопроверка для --check
│   ├── core/nanobot_config.py       — чтение настроек агента
│   └── …                            — поиск, карточка, хранилища
├── scripts/
│   ├── __init__.py
│   ├── follow_up_mcp                — лаунчер (POSIX)
│   └── follow_up_mcp.cmd            — лаунчер (Windows)
├── data/                            — рабочие данные (в git не попадают)
└── logs/server.log                  — stderr сервера (в git не попадает)
```

`.gitignore` навыка возвращает в git все каталоги `backend/` — корневое
правило `memory/` иначе срезало бы пакет `backend/core/memory` — и образец
`follow_up.env.local.example`, который накрывает корневое `*.env.*`.
Обычный `git add` их видит.

`backend/` сопровождается в репозитории Follow Up со своим набором тестов
и линтером и приезжает сюда готовым. Вложенный `ruff.toml` (с `extend` на
корневой `pyproject.toml`) исключает его из `ruff check` проекта и
включает лаунчер, у которого нет расширения `.py`.

## 13. Тесты

`tests/test_follow_up_skill.py` закрепляет контракт интеграции, а не
поведение D5:

- фронтматтер `SKILL.md`: имя совпадает с каталогом, `always: true`;
  в нём ровно семь инструментов `mcp_follow_up_*`, граница с
  `audit_analyzer` названа;
- в `config.json` нет записи `tools.mcpServers.follow_up`;
- лаунчер импортирует только стандартную библиотеку, `.cmd` на месте; код
  рядом находится без настройки; без кода — код 3, пустой stdout, причина
  в stderr; `--where` верно вычисляет `NANOBOT_HOME`;
  `follow_up.env.local` настраивает отдельный клон;
- инструменты агента совпадают с `tools.json` и `SKILL.md` (имена,
  описания, схемы); настоящий загрузчик проекта регистрирует ровно семь;
  секция `tools.follow_up.enable=false` их выключает;
- сервер поднимается заранее только в `gateway.py` (не с `--smoke`), один
  раз на семь инструментов; тесты проекта его не поднимают;
- мост на настоящем MCP-сервере-заглушке: вызов доходит с аргументами,
  окружение gateway доходит до сервера, сессия переживает смену цикла
  событий; сервер, умерший между вызовами, поднимается тем же вызовом, а
  умерший под тремя параллельными вызовами — не вешает их и не гасит
  замену; процесс, зависший на подъёме, действительно гасится; причина
  неподнявшегося сервера попадает в ошибку, журнал дописывается; журнал,
  который не открылся, сервер не останавливает; лишние аргументы серверу не
  передаются;
- ключ беседы и отправитель берутся из контекста хода nanobot;
- код D5 не импортирует проект, проект не импортирует код D5;
- `requirements.txt` D5 не переопределяет пакеты корневого;
- `ruff.toml` исключает `backend/` и включает лаунчер;
- рабочие данные игнорируются, и ни один файл навыка не срезан
  `.gitignore`.

```bash
python -m pytest tests/test_follow_up_skill.py -q
```

## 14. Запуск

### Production

1. Забрать ветку (или `master` после слияния).
2. Проверка тем же Python, что у gateway:

   ```bash
   python workspace/skills/follow_up/scripts/follow_up_mcp --check
   ```

   Если не хватает библиотек —
   `pip install -r workspace/skills/follow_up/requirements.txt` в
   окружение gateway и проверка ещё раз.
3. Перезапуск gateway **из корня репозитория**:

   ```bash
   python gateway.py --profile=prod
   ```

   В журнале — `Custom (project) tools: …` с семью `mcp_follow_up_*` и
   `follow_up: сервер навыка поднят`. В панели
   `PROJECT TOOLS INVENTORY: drift` они будут помечены `UNEXPECTED`: их нет
   в списке `canonical_project_tools()` проекта, а ветка существующие файлы
   не меняет. Это ожидаемо.
4. В чате Единого рабочего места выбрать К1-2 и спросить про акт проверки.

**Подготовка площадки** — один раз, скриптом
`migrate_to_agent_schema.py` из репозитория Follow Up: схема D5 и её
таблицы, представления над витринами, права групповым ролям схемы, модели
в каталоге нанобота и, если схема шины `public`, `GP_WRITE_SCHEMA` в `.env`
папки навыка. В этой ветке скрипта нет.

## 15. Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| Инструментов `mcp_follow_up_*` нет в `Custom (project) tools` | нет `workspace/tools/follow_up.py` или файлов навыка, либо `tools.follow_up.enable=false` | проверить файлы и настройку |
| `mcp_follow_up_*` помечены `UNEXPECTED` в панели drift | их нет в `canonical_project_tools()` проекта | ожидаемо, на работу не влияет |
| Вызов вернул «Follow Up сейчас недоступен» | сервер не поднялся: нет библиотек, нет интерпретатора, упал при старте; причина — в тексте ошибки | `logs/server.log` навыка; `follow_up_mcp --check` |
| Сервер завершается с кодом 2 | файлом базы владеет другой живой процесс Follow Up | остановить второй экземпляр (второй gateway, собственный сервер Follow Up) |
| В журнале сервера «файл владельца … не читается — считаю базу занятой» | файл владельца повреждён | если Follow Up нигде не запущен — удалить `data/index/followup.db.owner` |
| `status` показывает `greenplum: выключен` | у агента нет DSN, шина в обычном PostgreSQL или схема `public` | `follow_up_mcp --check`, раздел `gp`; схему — в `.env` папки навыка |
| `--check`: витрина не читается | нет представлений в схеме D5 | подготовка площадки (раздел 14) |
| «Follow Up не ответил за 240 с» | долгий вопрос или первый прогрев моделей | повторить; карточку — через `card_start`/`card_status` |
| Агент пересказывает таблицу своими словами | дословность — инструкция, а не механизм | факты и источники проверить по `sources` |

## 16. Инварианты сопровождения

- Ветка только добавляет файлы; `config.json` и `project.json` не меняются.
- Инструменты агента импортируют только стандартную библиотеку, `nanobot`,
  `mcp`, `anyio` и `loguru`; их описания и схемы — из `tools.json`, который генерируется из
  кода сервера.
- Лаунчер — только стандартная библиотека, и до запуска сервера он не
  пишет в stdout ни байта.
- Имена в `SKILL.md` — ровно `mcp_follow_up_<инструмент>` для семи
  инструментов сервера; тест это держит.
- В коде D5 нет адресов, имён баз и схем площадки, номеров реальных
  проверок и фактов из них.
- Код D5 не импортируется из `lib/` и других навыков и сам не импортирует
  код проекта.
- `requirements.txt` D5 не переопределяет версии пакетов корневого
  `requirements.txt`.
- `follow_up.env.local`, `.env`, `data/` и `logs/` навыка не коммитятся.
