# D5 — полное описание `follow_up`

## 1. Назначение документа

Этот документ описывает, как навык `follow_up` (далее — D5) подключается к
gateway: что лежит в этом репозитории, что — на машине, и как они
связываются.

Сама реализация D5 здесь **не лежит**. Она живёт в отдельном репозитории
Follow Up со своим окружением, моделями и данными, а gateway запускает её
отдельным процессом. В этом репозитории — только инструкция агенту, лаунчер и
одна запись в `config.json`.

Описание не содержит реальных актов, номеров проверок, строк подключения,
API-ключей, внутренних адресов и имён схем. Пути даны заглушками вида
`<путь>`.

## 2. Назначение D5

D5 отвечает по **текстам актов проверок и поручений**:

- что нашли в конкретной проверке, какие отклонения, что написано в акте;
- цитата из акта: где именно это сказано, в каких актах встречается тема
  или человек;
- гипотезы и перечень того, что стоит проверить, на старте новой проверки;
- карточка контроля исполнения по ответу профильного подразделения
  (письмо `.docx`, `.txt`, `.pdf`);
- реестр отклонений с фильтрами: категория, критичность, сумма, система,
  подразделение.

Граница с `audit_analyzer` простая: **текст акта и цитата — D5, агрегаты
по витринам и произвольный SQL — `audit_analyzer`**. Отказ одного навыка не
повод подменять его другим: «не нашёл» у D5 значит, что в корпусе актов
этого нет.

## 3. Положение в архитектуре

```text
чат Единого рабочего места (кнопка К1-2)
    │  вопрос в шину
    ▼
gateway (--profile=prod) → агент
    │  выбирает инструмент по SKILL.md и описаниям
    ▼
mcp_follow_up_ask / _hypotheses / _deviations / …      ← MCP, stdio
    │
    ▼
workspace/skills/follow_up/scripts/follow_up_mcp        ← лаунчер
    │  читает follow_up.env.local
    ▼
<интерпретатор Follow Up> -m backend.skill.mcp_server   ← отдельный процесс
```

**Почему отдельный процесс, а не `Tool` в gateway, как D3 и D6.** Причина
в зависимостях. У проекта жёстко закреплены `numpy==2.4.2`,
`faiss-cpu==1.13.2`, `duckdb`, `pyarrow`; у D5 — `numpy<2`, `torch`,
`sentence-transformers` (эмбеддер и реранкер). В одном окружении они не
уживаются: ломается либо синхронизация кэша gateway, либо модели D5.

MCP даёт отдельный интерпретатор, рабочий каталог и окружение, и это
штатный механизм `nanobot-ai` (`docs/TARGET_ARCHITECTURE.md`, §2.1: MCP —
часть generic runtime, вторые версии не создавать). Код проекта в `lib/`,
`gateway.py` и `config.py` не меняется.

## 4. Что меняет ветка

| Файл | Изменение |
|---|---|
| `workspace/skills/follow_up/SKILL.md` | новый — инструкция агенту |
| `workspace/skills/follow_up/scripts/follow_up_mcp` (+ `.cmd`) | новый — лаунчер |
| `workspace/skills/follow_up/follow_up.env.local.example` | новый — образец машинной настройки |
| `workspace/skills/follow_up/__init__.py`, `scripts/__init__.py` | новые, как у соседних навыков |
| `tests/test_follow_up_skill.py` | новый |
| `docs/D5.md` | новый — этот документ |
| `config.json` | **одна запись** в `tools.mcpServers`, до этого пустом |

`config.json` — единственный изменённый существующий файл, и обойтись без
него нельзя: `nanobot-ai` поднимает MCP-серверы только из
`tools.mcpServers` своего `Config`, а он читается из `config.json`. Ключи
из `.secrets.env` до этого объекта не доходят. Без записи процесс D5
просто никто не запустит.

`project.json` не меняется: своих таблиц и векторных индексов в runtime
gateway у D5 нет, а сам навык `SkillsLoader` находит по каталогу.

## 5. Подключение

### 5.1. Запись в `config.json`

```json
"tools": {
  "mcpServers": {
    "follow_up": {
      "type": "stdio",
      "command": "workspace/skills/follow_up/scripts/follow_up_mcp",
      "args": [],
      "tool_timeout": 120
    }
  }
}
```

Запись **одинакова на любой машине**: команда — путь к лаунчеру
относительно корня репозитория. В ней намеренно нет:

- абсолютных путей — это привязка к конкретной машине;
- подстановок `${VAR}` — `resolve_config_env_vars` бросает `ValueError` на
  неизвестной переменной, и gateway не стартовал бы там, где D5 не
  установлен.

`tool_timeout` поднят со штатных 30 до 120 секунд: обычный вопрос по
корпусу занимает 10–60 секунд. Всё, что дольше минуты, идёт задачей с
опросом (раздел 9).

Команда относительная, поэтому **gateway запускается из корня
репозитория** — то же допущение, что у `exec`-инструмента и в
`workspace/AGENTS.md`.

### 5.2. Лаунчер

`scripts/follow_up_mcp` — только стандартная библиотека, запускается
любым Python ≥ 3.8. Что он делает:

1. читает `workspace/skills/follow_up/follow_up.env.local`;
2. переменные окружения с теми же именами имеют приоритет над файлом;
3. вычисляет `NANOBOT_HOME` от собственного расположения — три уровня
   вверх от папки навыка, независимо от текущего каталога;
4. выставляет `PYTHONPATH`, `NANOBOT_HOME`, `MODELS_DEVICE` (по умолчанию
   `cpu`), `PYTHONUTF8`;
5. запускает `<FOLLOW_UP_PYTHON> -m backend.skill.mcp_server` в каталоге
   `FOLLOW_UP_ROOT` (на POSIX — через `exec`, тем же процессом).

На Windows `follow_up_mcp.cmd` вызывает лаунчер через `python` из `PATH`;
gateway находит `.cmd` по `PATHEXT` (`shutil.which` в
`_normalize_windows_stdio_command`) и оборачивает вызов в `cmd /c`.

### 5.3. `follow_up.env.local`

```text
FOLLOW_UP_ROOT=<путь к клону Follow Up>
FOLLOW_UP_PYTHON=<путь к интерпретатору его окружения>
MODELS_DEVICE=cpu
```

Файл попадает под `*.env.*` в `.gitignore` и **в git не коммитится**:
у каждой машины свои пути. Заполняется установщиком из репозитория
Follow Up (раздел 14) или вручную по `follow_up.env.local.example`.

### 5.4. Если D5 на машине не настроен

Лаунчер выходит с кодом 3, причину пишет в stderr; stdout остаётся чистым,
потому что это канал JSON-RPC. gateway логирует
`MCP server 'follow_up': failed to connect` и **стартует дальше** —
машины без Follow Up ничего не замечают.

Проверить настройку, ничего не запуская:

```bash
python workspace/skills/follow_up/scripts/follow_up_mcp --check
```

Ответ — JSON: найденные пути, итог `ok` и список проблем.

## 6. Инструменты

Имена у агента — `mcp_<сервер>_<инструмент>`.

| Инструмент | Что делает | Когда |
|---|---|---|
| `mcp_follow_up_ask` | вопрос по корпусу актов и поручений, ответ со ссылками на источники | основной путь |
| `mcp_follow_up_hypotheses` | гипотезы и что проверить по теме новой проверки | «начинаю проверку по теме X» |
| `mcp_follow_up_deviations` | реестр отклонений с фильтрами, без обращения к модели | нужна таблица, а не рассуждение |
| `mcp_follow_up_status` | что есть в корпусе и в каком режиме хранилище | отличить «не нашлось» от «этого тут нет» |
| `mcp_follow_up_card_start` | запустить сборку карточки исполнения, сразу возвращает `job_id` | прислан ответ подразделения |
| `mcp_follow_up_card_status` | стадия и результат по `job_id`, сам ждёт до 20 с | после `card_start`, пока `done=false` |
| `mcp_follow_up_forget` | забыть контекст диалога | аудитор перешёл к другой проверке |

## 7. Модель

**Своей модели у D5 нет — она берётся у агента**, тем же правилом, что у
`audit_analyzer`: `agents.defaults.provider` и `model` плюс
`providers.<provider>.apiBase` и `apiKey`. Переопределения —
`skills.follow_up.llm.{max_tokens, temperature}` (единственная форма,
которую пропускает `SkillSettings`).

Файлы читаются из `NANOBOT_HOME` в том же порядке, что у gateway
(`project.json` → `config.json` → `.secrets.env`, затем `${VAR}`).
Администратор меняет модель в одном месте — D5 идёт за ней. Ключ в журнал
не пишется.

Эмбеддер и реранкер D5 работают **на CPU** (`MODELS_DEVICE=cpu`):
видеокарты на машине gateway заняты обслуживанием основной модели, и три
гигабайта D5 уронили бы не его, а её.

## 8. Сессии и память диалога

D5 помнит, о какой проверке шла речь, и доигрывает уточнения. Память
ключуется параметром `session_key`.

Модель агента свой ключ сессии не видит: в системном промпте его нет, а
MCP-обёртка контекст запроса не передаёт. Поэтому `session_key` во всех
инструментах **необязателен**. Если он не передан, D5 использует общий
ключ — это деградация памяти диалога, а не поломка: контекст беседы у
агента свой. `SKILL.md` просит агента передавать стабильный идентификатор
беседы.

## 9. Долгие операции

Карточка исполнения строится минутами.

1. `mcp_follow_up_card_start` возвращает `job_id` сразу.
2. `mcp_follow_up_card_status` **сам ждёт** готовности до 20 секунд
   (`wait_sec`, максимум 60).

Ожидание на стороне сервера, потому что у агента нет паузы между вызовами:
получив «не готово», он позвал бы снова немедленно и за секунды сжёг
лимит итераций.

## 10. Контракт доставки

Успешный ответ приходит полем `answer_md` — готовым текстом. `SKILL.md`
требует выводить его дословно, без summary-pass и своего вступления, — тот
же контракт, что у D3 и D6.

Это **инструкция модели, а не механизм**: переформулировка возможна.
Факты и нумерация источников на практике сохраняются.

Прочие поля:

| Поле | Значение |
|---|---|
| `ok: false` + `reason` | честный отказ: в корпусе этого нет, нужен номер проверки |
| `clarify` | D5 просит уточнение — задать пользователю дословно и позвать снова |
| `insufficient: true` | найдено мало, D5 говорит об этом сам |

## 11. Данные

У D5 свой локальный корпус (SQLite, FAISS, BM25) и свои таблицы в
корпоративной БД. Витрины-источники — только на чтение; вердикты аудиторов
пишутся только в собственную таблицу D5.

Локальная SQLite открыта без файловых блокировок (так она работает на
сетевом хранилище), поэтому **владелец у файла базы один**. Если файлом уже
владеет другой живой процесс Follow Up, MCP-сервер отказывается стартовать
с кодом 2 — два писателя без блокировок портят базу. Собственный
веб-сервер Follow Up с тем же каталогом данных на машине gateway не
запускать.

## 12. Структура каталога

```text
workspace/skills/follow_up/
├── SKILL.md                         — инструкция агенту
├── __init__.py
├── follow_up.env.local.example      — образец машинной настройки (см. ниже)
├── follow_up.env.local              — сама настройка (в git не попадает)
└── scripts/
    ├── __init__.py
    ├── follow_up_mcp                — лаунчер (POSIX)
    └── follow_up_mcp.cmd            — лаунчер (Windows)
```

**Образец лежит в git вопреки правилу `*.env.*`** в `.gitignore` — оно
накрывает и его. Добавлен принудительно (`git add -f`), ровно как
`.secrets.env.example` в корне. Секретов в нём нет, только заглушки путей.
При пересоздании файла `-f` понадобится снова: без него git молча его
пропустит, а `SKILL.md` и раздел 14 ссылаются на этот образец.

## 13. Тесты

`tests/test_follow_up_skill.py`:

- фронтматтер `SKILL.md`: имя совпадает с каталогом, `always: true`;
- в `SKILL.md` ровно семь инструментов `mcp_follow_up_*` — не больше и не
  меньше;
- граница с `audit_analyzer` названа;
- запись в `config.json` статична: без абсолютных путей и `${VAR}`;
- лаунчер импортирует только стандартную библиотеку, `.cmd` на месте;
- без настройки — код 3, пустой stdout, причина в stderr;
- `--check` объясняет, чего не хватает, и верно вычисляет `NANOBOT_HOME`;
- `follow_up.env.local` действительно настраивает лаунчер.

```bash
python -m pytest tests/test_follow_up_skill.py -q
```

## 14. Запуск

### Production

1. Клон Follow Up на постоянное хранилище, его окружение и модели — по
   инструкции репозитория Follow Up.
2. Настройка из репозитория Follow Up:

   ```bash
   python scripts/install_into_nanobot.py --nanobot <корень gateway> --python <интерпретатор Follow Up>
   ```

   Он пишет `follow_up.env.local` и проверяет всё, что увидит gateway.
   Без установщика — скопировать `follow_up.env.local.example` в
   `follow_up.env.local` и заполнить.
3. Проверка: `python workspace/skills/follow_up/scripts/follow_up_mcp --check`.
4. Перезапуск gateway **из корня репозитория**:

   ```bash
   python gateway.py --profile=prod
   ```

   В логе — `MCP server 'follow_up': connected, 7 capabilities registered`.
5. В чате Единого рабочего места выбрать К1-2 и спросить про акт проверки.

## 15. Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| В логе gateway нет `MCP server 'follow_up'` | нет записи в `config.json` | проверить `tools.mcpServers.follow_up` |
| `MCP server 'follow_up': failed to connect` | лаунчер вышел с кодом 3 — нет или неполон `follow_up.env.local` | причина в stderr рядом; `follow_up_mcp --check` |
| То же, файл заполнен | gateway запущен не из корня — относительная команда не нашлась | запускать из корня репозитория |
| Процесс D5 сразу завершается с кодом 2 | файлом базы владеет другой живой процесс Follow Up | остановить второй экземпляр |
| Первый вопрос упирается в `tool_timeout` | модели греются при первом обращении | повторить; дальше они в памяти |
| Агент пересказывает таблицу своими словами | дословность — инструкция, а не механизм | факты и источники проверить по `sources` |

## 16. Инварианты сопровождения

- Запись в `config.json` остаётся статичной: без абсолютных путей и без
  `${VAR}`.
- Лаунчер — только стандартная библиотека, и до запуска Follow Up он не
  пишет в stdout ни байта.
- Имена в `SKILL.md` — ровно `mcp_follow_up_<инструмент>` для семи
  инструментов сервера; тест это держит.
- `follow_up.env.local` не коммитится.
- Код Follow Up не импортируется из `lib/`, `workspace/tools/` и других
  навыков; общего окружения с gateway у него нет.
